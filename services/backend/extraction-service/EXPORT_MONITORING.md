# Wearables export monitoring

The extraction service instruments the CSV and FHIR export routes at the ASGI
boundary. The scope starts before request validation and ends when the application
finishes sending the response or the request terminates. A 200 response header
alone cannot mark an export successful.

| Prometheus metric | Type | Labels | Counts or measures |
|---|---|---|---|
| `wearables_export_requests_total` | Counter | format | Requests reaching either exact export route |
| `wearables_export_completed_total` | Counter | format, outcome | One terminal outcome per request |
| `wearables_export_duration_seconds` | Histogram | format, outcome | Monotonic elapsed seconds through the terminal outcome |
| `wearables_export_active` | Gauge | format | Requests currently in progress |
| `wearables_export_measurements_considered_total` | Counter | format | Readings yielded after filtering, deduplication and existing reconciliation |
| `wearables_export_measurements_exported_total` | Counter | format | Readings successfully serialized, including partial exports |
| `wearables_export_measurements_omitted_total` | Counter | format, reason | Readings deliberately skipped by the renderer |

`format` is `csv` or `fhir`. `success` requires a final ASGI body message
accepted by the server and a normal return. Empty valid files count as successful.
`rejected` covers completed 4xx responses from extraction, including query
validation. `cancelled` covers observed disconnects and task or generator
cancellation. `failed` covers exceptions, server errors and incomplete responses
without a disconnect signal. The active gauge is decremented in all cases.
The response closes its generator when streaming unwinds.

The only currently observable deliberate omission is `unsupported_mapping`,
when the existing FHIR builder returns no observation. CSV retains its current
handling of missing and nonnumeric values. Exceptions during reading or
serialization fail the export without counting a deliberate omission. A reading
that caused a serialization failure is considered but neither exported nor
omitted. CSV headers and FHIR envelope bytes are outside the reading counters.
Only fixed labels appear in the registry. It contains no request parameters,
identifiers, exceptions, filenames or measured values.

Success is observed at the extraction server boundary. The server cannot confirm
receipt by the browser, and a proxy may buffer the response or maintain the
upstream connection after a client disconnects. Authentication and authorization
rejections generated by the BFF never reach this instrumentation. A process
terminated abruptly can lose in-flight outcomes and increments between scrapes.

## Local demonstration

From this directory, run `./demo/run.sh` with Docker Engine, Docker Compose v2,
curl and Python 3. The script builds the extraction image and starts a synthetic
NDJSON backend, Prometheus and Grafana. It waits for the first successful scrape
before sending valid CSV and FHIR requests, an invalid query and a request whose
upstream returns 503. The 503 occurs during streaming, so curl reports an
incomplete download even though it received 200 headers.

- Grafana dashboard: <http://127.0.0.1:13000/d/wearables-export-monitoring>
- Prometheus targets: <http://127.0.0.1:19090/targets>
- Raw metrics: <http://127.0.0.1:19103/metrics>

Stop the demo with `docker compose -f demo/compose.yaml down`. All published
demo ports bind to loopback. The demo backend provides generated readings only.

For Python development, use `uv sync --locked`, then `uv run pytest -q`.
Run `uv run ruff check src/app/{main,metrics,serve}.py tests/test_export_metrics.py demo/db_lord.py`
in Bash. To run the API and metrics listener without Docker, use
`uv run python -m src.app.serve` with `DB_LORD_BASE_URL` pointing to a local
backend. `METRICS_PORT` defaults to 9103. Set it to 0 to disable the separate
listener. A bind error fails startup. The supported launcher explicitly runs
one Uvicorn worker per pod and shuts down the metrics listener on exit. Scale
with pod replicas. Multiprocess registry mode is deliberately unsupported.

## Kubernetes and Grafana

The extraction chart exposes `metrics.port` on a separate ClusterIP service
when `metrics.enabled` is true. Neither the existing public API service port nor
the BFF routes direct traffic to the metrics listener. Prometheus uses pod
discovery with the configured `scrape.extractionService.namespace` and release
label, and scrapes each Running pod on its named metrics port. Its existing
pod discovery RBAC covers the new job. Enable the chart settings with an
extraction image containing this implementation.

The Grafana chart provisions the dashboard from its `dashboards` directory
using the existing Prometheus datasource. Range totals use per-pod counter
increases before aggregation. These are Prometheus estimates bounded by scrape
resolution and observed counter resets. Success rate divides successes by all
terminal outcomes and has no value without completions. Latency quantiles use
successful requests and retain the format dimension. Counts and rates retain
their natural missing-data behavior when no matching series are scraped.
