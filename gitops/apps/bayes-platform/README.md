# BayesPlatform

Self-contained install of [bayesimpact/bayes-platform](https://github.com/bayesimpact/bayes-platform) (public chart and images) in the `bayes-platform` namespace, with bundled Postgres and Redis.

The cluster API is only reachable through the de.NBI jumphost (`ssh -N -D 127.0.0.1:18080 denbi-jumphost-01.bihealth.org`, then `export HTTPS_PROXY=socks5://127.0.0.1:18080`).

## Secrets (once)

Fresh values, generated locally and never written to the repo:

```sh
kubectl create namespace bayes-platform
openssl genrsa -out priv.pem 2048 && openssl rsa -in priv.pem -pubout -out pub.pem
kubectl -n bayes-platform create secret generic bayes-platform-secrets \
  --from-literal=MCP_ENCRYPTION_KEY="$(openssl rand -hex 32)" \
  --from-file=APPS_JWT_PRIVATE_KEY=priv.pem --from-file=APPS_JWT_PUBLIC_KEY=pub.pem
rm priv.pem pub.pem
```

The bundled Postgres password is generated by the chart. LLM keys (`VLLM_*` and others) are added to the same Secret later.

## Install / upgrade

The chart only exposes a nodeSelector for the API and the CPU workers, so a kustomize post-renderer (`post-render/`) pins every workload to the dedicated node. Helm 3 does not post-render hooks, so upgrades run with `--no-hooks`; helm runs in a container because it is not installed locally:

```sh
docker run --rm -v ~/.kube/config:/root/.kube/config:ro -v "$PWD":/work -w /work \
  -e HTTPS_PROXY=socks5://host.docker.internal:18080 --entrypoint helm alpine/k8s:1.31.13 \
  upgrade --install bayes-platform oci://ghcr.io/bayesimpact/charts/bayes-platform \
  --version 26.9.4 -n bayes-platform -f values.yaml \
  --post-renderer ./post-render/post-render.sh --no-hooks --timeout 10m
```

When the chart version changes, run the migration Job by hand on bayes-node (`helm template --show-only templates/migrate-job.yaml`, add `nodeSelector: {workload: bayes}`, `kubectl apply`), otherwise it pulls the large app image onto a wearables node.

## Open

- OIDC provider: placeholder, so sign-in does not work yet.
- LLM access and Vertex embeddings: not configured.
- Ingress: disabled. The `urls` are in-cluster placeholders until the public paths on wearables.charite.de are decided.

## Node

The `wearables-node` machines have 19 GB disks: pulling the API and worker images put one of them into `DiskPressure` on the first install. All BayesPlatform workloads therefore run on a dedicated node, added as the Kubermatic MachineDeployment `bayes-node` in `kube-system` (flavor `de.NBI small`: 8 vCPU / 16 GB, 100 GB root disk, node label `workload=bayes`; the chart asks for at least 4 vCPU, 8 GiB and 80 GiB free).

## Keycloak (temporary login provider)

`keycloak.yaml` runs Keycloak 26.2 in dev mode in this namespace, with a `platform` realm (client `platform-web`, one user) imported on every start. It will be replaced by another Keycloak later. Secrets, created once and never in the repo (letters and digits only, so they copy cleanly):

```sh
pw() { LC_ALL=C tr -dc 'A-Za-z0-9' </dev/urandom | head -c 20; }
kubectl -n bayes-platform create secret generic bayes-keycloak \
  --from-literal=KC_BOOTSTRAP_ADMIN_PASSWORD="$(pw)" \
  --from-literal=BAYES_USER_EMAIL=<your email> \
  --from-literal=BAYES_USER_PASSWORD="$(pw)"
kubectl apply -f keycloak.yaml
```

Everything is reached through port-forward for now; the OIDC issuer is fixed to `http://localhost:8180/realms/platform`, and a sidecar in the API pod makes that URL work inside the cluster:

```sh
kubectl -n bayes-platform port-forward svc/keycloak 8180:8080             # admin console: http://localhost:8180/admin/
kubectl -n bayes-platform port-forward svc/bayes-platform-api 8181:3000   # BayesPlatform: http://localhost:8181
kubectl -n bayes-platform get secret bayes-keycloak -o jsonpath='{.data.BAYES_USER_PASSWORD}' | base64 -d; echo
```
